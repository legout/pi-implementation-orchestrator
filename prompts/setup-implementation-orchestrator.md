# Setup Implementation Orchestrator

Deterministic setup for this request: `$@`. All inspection, validation, and mutation happen in the package's `setup.sh`; never edit project files or install skills yourself.

1. **Locate the package and choose the operation once.** Use `./setup.sh` when this checkout *is* the package; otherwise run `pi list` once and use the installed `legout/pi-implementation-orchestrator` copy's `setup.sh`. Never run an unrelated project's `setup.sh` just because it exists. If it cannot be located or is ambiguous, ask for the checkout/package path. Treat `update`, `upgrade`, or `--update` anywhere in the additional input `$@` as an update request and include `--update` in every setup command; treat `migrate` or `--migrate-namespace` as a request to move legacy `docs/` artifacts to `project/` and include `--migrate-namespace` in every setup command; otherwise use normal install/reconfigure mode. Update mode uses the currently installed package version—it does not update this package itself (`pi update git:github.com/legout/pi-implementation-orchestrator` does that separately).
2. **Inspect — only when inputs are not fully explicit.** If the request already supplies the operation, target project (or an explicit `--skip-project`), every choice flag (`--instruction-file`, `--tracker`, `--domain-layout`, `--skill-scope`, `--worker-model`, `--reviewer-model`, `--worker-thinking`, and `--reviewer-thinking`), and an explicit custom-content decision (`--replace-custom` when replacement is intended), skip this step. Otherwise ask for the missing target project first, then run `setup.sh --inspect` once with the known flags. It is read-only, needs no answers, and reports detected configuration, current worker/reviewer settings, unresolved choices, custom content in the managed docs (`project/agents/artifacts.md`, `project/agents/issue-tracker.md`, `project/agents/domain.md`; legacy installations keep `docs/agents/`), MCP configuration hazards, and the selected Epiq config target when applicable. When either role lacks explicit model flags, run `pi --list-models` at most once and offer each role: **Keep existing (recommended)**, **Inherit parent**, or one available `provider/model`; offer thinking independently as keep, inherit/default, or an available level. Collect every unresolved choice — including whether to replace custom content in any managed doc — and ask the user **all of them in one grouped round**. If replacement is approved, include `--replace-custom` in both later commands; if it is declined, stop rather than attempt an apply that would refuse the custom content. Do not guess through contradictory files, do not read project files one by one, and do not open help, planning skills, or subagents for setup discovery.
3. **Preview.** Run `setup.sh --dry-run` once with fully explicit flags (including `--update` for update requests, all four model/thinking flags, and `--replace-custom` when approved) and show its complete output verbatim (install/update commands, skipped missing or pinned components, the resulting subagent settings, and the exact resulting project files). In update mode, stop if inspect reports no existing installation at the selected scope.
4. **Approve.** Request explicit approval for that exact preview. Any changed choice restarts at step 3 with a new preview.
5. **Apply.** Run the identical command with `--dry-run` removed and `--yes` added, then report what actually happened (skills/packages installed or updated, settings/files written). Normal mode installs the selected runtime skills from `legout/skills` — including the shared `planning-contract` skill that owns planning artifact and handoff semantics — with `npx skills` and the `pi-subagents`/`pi-intercom` packages; selecting Epiq also installs `pi-mcp-adapter`. Update mode requires an existing selected-scope installation, runs `npx skills update` only for managed `legout/skills` entries present in that scope, runs `pi update` only for matching unpinned packages present in that scope, skips missing/pinned components instead of installing them, refuses cross-scope package updates that Pi cannot isolate, and refreshes only changed managed files. An explicit `--bin-link` request (also when the additional input asks for the `pi-orchestrator-init` command) creates the `~/.local/bin/pi-orchestrator-init` symlink to the pi-managed clone's `setup.sh`; it is refused from a checkout or extracted tarball and never overwrites an existing file. Nothing is installed, updated, or written before approval. Project outputs (`project/agents/artifacts.md`, `project/agents/issue-tracker.md`, `project/agents/domain.md`, and the managed instruction-file block) are written afterward; Epiq additionally merges `epiq-mcp` into `.mcp.json` for project scope or `~/.config/mcp/mcp.json` for global scope, preserving other servers and refusing conflicts. Setup does not initialize an Epiq board or project. Explicit model/thinking choices update only those worker/reviewer fields in the selected scope's Pi settings; `keep` is the default and preserves existing global overrides. If a write fails, report the nonzero failure and tell the user to rerun setup to converge. The generated workflow routes implementation to builtin `worker` and fresh independent review to builtin read-only `reviewer`; setup does not create or replace agent definitions. Confirm both profiles are executable before dispatch and record the resolved names in the run manifest.

**Bound after package/target resolution:** at most three script executions (inspect, preview, apply), one read-only `pi --list-models` query when model choices are needed, one grouped choice round, and one approval. Invalid input, validation hazards (for example symlinked instruction files or malformed managed markers), and failures are legitimate exceptions — report them instead of improvising.

Native package loading stays passive: installing this package never runs setup or creates project files; setup runs only through this prompt or direct `setup.sh` use.
